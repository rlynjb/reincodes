# Chapter 00 — Overview

## The codebase in one paragraph

reincodes is a Next.js 15 static-export app — TypeScript, React 19, Tailwind, deployed to GitHub Pages at the basePath `/reincodes`. Two things share the bundle: a portfolio home page composing Hero / FeaturedProjects / Concepts / Implementations / Footer, and a set of interactive algorithm visualizers under `/sorting`, `/trees`, `/recursions`, `/graphs`. No backend, no API, no database, no AI surface in production. Every visualizer page is `"use client"`, owns its own React state, and runs an animation loop of the shape *mutate state → `await delayLoop(speed)` → mutate state*. Reference data structures (Tree, BinarySearchTree, BinaryHeap, PriorityQueue, Graph, Graph2, PG) live in `src/utils/data_structures/` and are imported by the pages that animate them. The whole site builds to static HTML/JS and ships through a single GitHub Actions workflow.

## The staff-engineer's overall take

**Take:** reincodes is a teaching artifact that has correctly chosen Locality of Behaviour as its load-bearing principle and is paying the predictable cost of that choice in three places: drift between parallel classes, dead code shaped like algorithms, and small bugs in pages that all look almost-but-not-quite the same. The codebase is *well-composed for what it is* and the things a habituated DRY/SRP eye flags as violations are mostly the design working as intended. The interesting weaknesses are not where conventional wisdom points; they're in the seams where the duplication isn't legible duplication — it's drift that happened over time and stopped being equivalent.

The pattern of the codebase's strengths is consistent. Concrete-by-design — no premature abstraction, no DI ceremony, no interfaces invented in case a second implementation appears that never will. Generators used where they earn their keep (`Tree.preOrderTraversal`). The one real DSA optimization in the codebase (the `valueIndicesLookup` dict in `PriorityQueue.ts` that makes Dijkstra O((V+E) log V) instead of O(V²)) is correct, well-placed, and quietly load-bearing. The animation contract is unusual for React but right for the use case — the alternative (`requestAnimationFrame` driving a state machine) would scatter the algorithm across multiple files and lose the entire reason a reader opens `bubble-sort/page.tsx` in the first place.

The pattern of the codebase's weaknesses is also consistent, and is the cost of the same design. The visualizer pages share enough skeleton that small bugs land in one and not the others — `heap-sort/page.tsx` ignores the user's `speed` slider in three places, `merge-sort/page.tsx:154` hardcodes `delayLoop(100)`, and the merge sort comparator uses strict `<` so it isn't stable despite merge sort being canonically stable. These would be impossible if the skeleton were unified; they're cheap to live with as long as the answer to "should we unify?" stays no. Separately, `DijkstrasAlgorithm.ts` is broken at runtime (snake_case `num_nodes` and `to_node` against the camelCase fields in `Graph2`) and has no callers — it's dead code shaped like an algorithm, which is the most misleading kind of file in a teaching codebase, because a reader navigating to find the Dijkstra implementation finds it, reads it, and concludes the codebase ships it. `MinHeap` and `MaxHeap` have drifted (`MinHeap` carries `getMinSwapSequence` that `MaxHeap` doesn't), which would be impossible under a parameterized `BinaryHeap<T>(compare)` and is the only place in the codebase where the DRY argument cleanly wins. And several `_iterative` variants of BST methods reference fields that don't exist (`.value` where the field is `.key`, `BinaryTreeNode` where the class is `BSTNode`) — dead study-notebook code that ships in the same module as the methods that work.

**The one thing I'd change** if I could only change one: stop shipping dead code that's shaped like working algorithms. Either fix `DijkstrasAlgorithm.ts` and the iterative BST variants and connect them to callers, or move them to the existing `src/utils/notes/` folder where the rest of the study-notebook code lives. That decision unblocks the harder ones (do we collapse MinHeap/MaxHeap? do we finish the `Graph` → `Graph2` migration? do we rename `Graph2`?) because it forces the question of what the `src/utils/data_structures/` directory *is*: a working library, or a working library plus reference implementations? Right now it's both, undeclared, and the reader can't tell which file is which without running the code.

## Reading order and chapter summaries

There are five working chapters. The takes build on each other within a chapter; don't graze across chapters. Each chapter should take 20–40 minutes to read end-to-end. The recommended order is **05 → 03 → 01 → 02 → 04**, which goes "design philosophy → most actionable refactor → clean wins → the central refactor that isn't ready yet → the chapter where the codebase doesn't need much."

**Chapter 01 — Composition refactors** (DEEP: 2, BRIEF: 4, MENTION: 6). The clean win is **Parameterize Function** on MinHeap/MaxHeap, which is the one place DRY-with-care lands cleanly and where the parallel classes have already drifted. The other DEEP, **Extract Function** on the animation loop, gets a more nuanced verdict — Extract Function as a standalone refactor doesn't quite earn its place because the candidates either save two lines or collapse into the Chapter 03 shell extraction. The MENTIONs are mostly small surface bugs (`merge-sort` hardcoded delay, `heap-sort` ignoring `speed`, dead `_iterative` BST methods) — quick housekeeping wins.

**Chapter 02 — Structural refactors** (DEEP: 1, BRIEF: 4). The chapter has one DEEP and it's the most-discussed refactor in the book: **Separate Pure from Effectful** via generator-yielded steps. The pattern is already proven in this codebase (`Tree.preOrderTraversal`) and the payoff is real (testability, scrub-back, step controls). The verdict is *not yet*: it pays back the day a scrub feature is requested, not before. The BRIEFs include the **Inline Module** verdict that says delete `DijkstrasAlgorithm.ts` and the commented-out `shortest_path.ts`, which is the easiest user-visible win in the book.

**Chapter 03 — Design patterns** (DEEP: 2, BRIEF: 3, MENTION: 1). The two DEEPs are **Strategy** and **Iterator**, and they're really one refactor with two framings. The Strategy verdict is *shell extraction, not full Strategy* — extract a `<SortingShell>` that handles input/speed/run/reset, but leave the algorithm visible in each `page.tsx`. The Iterator verdict is *staged rollout of the generator pattern* starting with `MinHeap`'s swap recording, then sorting algorithms, then graph traversals. Most of the catalog is NOT FOUND, which is the right answer for a codebase of this size and shape.

**Chapter 04 — DSA refactors** (DEEP: 1, BRIEF: 4, MENTION: 4). The shortest chapter and intentionally so. The one DEEP (**Batch / Debounce / Throttle**) is really a discussion of whether to batch `setState` updates within a single algorithmic step — interesting but not load-bearing. The chapter's actual take is that this codebase doesn't need DSA refactors — its algorithms are slow on purpose, the animation IS the perf cost, and the one real optimization (`valueIndicesLookup`) has already happened. The remaining BRIEFs reframe perf-looking findings as dead-code cleanups, which is what they actually are.

**Chapter 05 — Principles** (DEEP: 4, BRIEF: 3, MENTION: 1, NOT FOUND: 2). The chapter with the highest-stakes content and the most interesting paragraph in the book. Four DEEP principles (**Single Responsibility, DRY-with-care, Separation of Concerns, Locality of Behaviour**) are the same root tension viewed from three angles, with DRY independently DEEP because the three duplication sites (MinHeap/MaxHeap, sorting pages, Graph/Graph2) each warrant a different verdict. The chapter close — *which principles this codebase honours by default and which it strains against* — is the take that distinguishes this book from a generic refactor checklist. Read this chapter first. The chapter close is the take that the rest of the book is downstream of.

When you're ready to actually do something, the book hands off to `/aipe:audit-cleanup` (triage what to act on) and then to `/aipe:refactor` (execute one named refactor). Don't treat the verdicts as a queue; they're opinions, not work items.
