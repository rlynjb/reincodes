# State-space BFS

**Industry name(s):** State-space search, implicit-graph BFS, configuration-space search
**Type:** Industry standard · Language-agnostic

> BFS over a graph that doesn't exist in memory until the search starts — nodes are problem *states* (e.g. `{guards_left, prisoners_left, boat_side}`), edges are *valid moves*, both generated on demand by a transition function.

**See also:** → 14-graph-adjacency-list.md · → 15-bfs-with-parent-tracking.md · → 17-dijkstras-shortest-path.md

---

## Why care

You're building a multi-step form wizard. The user starts on step 1 ("choose plan"). Depending on their selection, step 2 is one of three different forms ("enter card", "enter bank", "skip — free tier"). Each of those leads to more branches. There are dozens of valid wizard paths and you want to find the shortest one — the fewest screens between "start" and "submitted." But you can't list every possible wizard state up front; the branching depends on what the user picks at each step. The state graph is *implicit* — it only exists in the form's transition rules.

That implicit-graph search is exactly what state-space BFS solves. Not the "search a maze" framing — the *wizard-shortest-path* framing. The "start node" is the initial wizard state. The "edges" are valid transitions from any given state. The "shortest path" is the minimum number of moves to reach the goal state. You never write down the full graph — you just walk it as you go, asking the transition function "from here, what's reachable?" at every step.

**Why you need to answer that question at all:** because many problems don't come with a graph. The river-crossing puzzle in reincodes (`/graphs/river-crossing-puzzle`) is the cleanest example — three guards, three prisoners, one boat, a rule that prisoners outnumbering guards on either shore loses. There's no graph file. No edge list. Just a `PGState` (guards on left, prisoners on left, boat side) and a rule for what counts as a valid move. The "graph" of all configurations and moves only takes shape when BFS asks "from this state, what's next?" and a transition function answers.

Without state-space BFS:
- You'd have to enumerate every valid configuration up front, then build an edge list, then run regular BFS
- Adding a constraint (e.g., "boats can hold 3 people now") means rebuilding the whole graph
- For problems where the state space is too large to fully materialize (15-puzzle has ~10^13 states), enumeration is impossible — but lazy search visits only the reachable, useful portion

With state-space BFS:
- Two functions are all you write: `neighbors(state)` and `state.toString()` (for hashing visited states)
- The "graph" grows during search; only states actually reached get allocated
- Same algorithm shape as BFS-with-parent — FIFO queue, visited set, parent pointers — just with object-state instead of integer-index

State-space BFS is BFS over an implicit graph generated by a transition function. The form-wizard analogy holds exactly: each wizard state knows its "next valid steps," and you walk to the goal in fewest moves. The full mechanics are below.

## How it works

### Move 1 — The mental model: BFS where neighbors are generated, not stored

Picture the BFS loop from `breadth_first_search` — pull the front of the queue, look at the current node's neighbors, push the unvisited ones. Now imagine the neighbors aren't stored in `graph.nodes[u].edges`. They're computed by calling a function: `pg_neighbors(state)`. The function takes a state, generates every possible move from that state, validates each one against the puzzle's rules (no prisoners can outnumber guards on either shore), and returns the surviving moves as new states.

```
Standard BFS                     State-space BFS

  queue.shift() → u                queue.shift() → state
       │                                │
       ▼                                ▼
  for edge in g.nodes[u].edges:    for state in pg_neighbors(state):
    look up neighbor                  generate neighbor on the fly
    push if unvisited                 push if state.toString() not in visited
```

The strategy in one line: replace "look up neighbors in storage" with "compute neighbors from a transition function." The outer BFS shape — FIFO queue, visited set, parent pointers — is unchanged.

### Move 2 — The four pieces of state-space-BFS state

`solve_pg_bfs` in `PG.ts` carries the same shape as a regular BFS, but each piece adapts to the implicit-graph case.

**Sub-section A: the `PGState` — a problem-specific node**

`PGState` is a small object that captures everything about the puzzle at one moment. Three fields, fully ordered:

```
class PGState:
  guards_left:    number     // 0..3
  prisoners_left: number     // 0..3
  boat_side:      "L" | "R"

  toString(): `${guards_left},${prisoners_left},${boat_side}`
```

The bridge from frontend: this is the same shape as a form's `useState` object — the entire UI is a function of this object, and any change to it triggers a re-render. Here, the entire "graph node" is the state object; any change produces a *new* node.

`toString()` is critical. Two states are "the same node" if and only if their string representations match. For the river-crossing puzzle, that means same number of guards on the left shore, same number of prisoners on the left shore, same boat position. Different objects with identical fields are the same node.

**Sub-section B: the `visited` dict — keyed by `state.toString()`**

In regular BFS, `visited` is a `boolean[V]` because nodes have known integer indices. In state-space BFS, you don't know V up front, and node identity isn't an integer. So `visited` becomes a `Record<string, number>` mapping state strings to *node indices* in the graph being built:

```
visited["3,3,L"] = 0    // initial state, mapped to graph node 0
visited["2,2,R"] = 1    // 2 guards + 1 prisoner crossed to right
visited["3,2,L"] = 2    // guard came back with one prisoner
...
```

The values are indices into a `Graph2` instance that grows as new states are discovered. Storing the index lets `solve_pg_bfs` later run `breadth_first_search` over the materialized graph and reconstruct paths using the standard `parent`-array trick.

Practical consequence: state hashing replaces visited[node]. The hash is what makes "is this state new?" an O(1) check. Get the `toString()` wrong (two different states produce the same string) and BFS misses solutions; get it too unique (the same state produces different strings) and BFS revisits states and loops.

**Sub-section C: `pg_neighbors(state)` — the transition function**

This is the heart of the algorithm. Given a state, return every valid next state. For the river-crossing puzzle:

```
moves = [[1,0], [2,0], [0,1], [0,2], [1,1]]
        // [num_guards, num_prisoners] for each possible boat load

function pg_neighbors(state):
  neighbors = []
  for move in moves:
    next_state = pg_result_of_move(state, move[0], move[1])
    if next_state is valid:
      neighbors.push(next_state)
  return neighbors
```

`pg_result_of_move` (`PG.ts` L24–L72) does two jobs: arithmetic (subtract from current side, add to other side, flip boat) and validation (no negative counts, prisoners can't outnumber guards on either shore). Invalid moves return `null`; `pg_neighbors` filters them out.

The bridge from frontend: this is the same pattern as a state-machine library's `transitions[currentState]` map — given where you are, here are the moves you're allowed. XState's transition objects, Redux's reducer cases, formik's onSubmit handlers — all the same shape: state → next state, constrained by rules.

**Sub-section D: the lazy graph build — `Graph2` grown during search**

`create_prisoners_and_guards` (L87–L141) does the heavy lifting. It builds a `Graph2` *during* a BFS-like walk, inserting nodes for every new state and edges for every valid move. After this function returns, the entire reachable state space is materialized as a regular `Graph2` — and the standard `breadth_first_search` can run on it.

```
function create_prisoners_and_guards():
  visited = {}              // state.toString() → graph index
  queue   = []
  g       = new Graph2(0, undirected=true)

  initial_state = new PGState(3, 3, "L")
  initial       = g.insertNode(initial_state)
  queue.push(initial.index)
  visited[initial_state.toString()] = initial.index

  while queue.length > 0:
    current_ind   = queue.shift()
    current_node  = g.nodes[current_ind]
    current_state = current_node.label

    for state in pg_neighbors(current_state):
      state_str = state.toString()
      if state_str not in visited:
        new_node              = g.insertNode(state)
        visited[state_str]    = new_node.index
        queue.push(new_node.index)
      // edge always inserted (even if neighbor already visited)
      g.insertEdge(current_ind, visited[state_str], 1.0)

  return g
```

Two things to notice:
1. The first BFS walk (inside `create_prisoners_and_guards`) discovers the state space and builds the graph.
2. A second `breadth_first_search` call (inside `solve_pg_bfs`) runs the standard parent-tracking BFS on the now-materialized graph to find the shortest path from initial to goal.

The two-pass shape is a deliberate split between "discover the graph" and "find the path." You could do both in one pass — but reusing the standard `breadth_first_search` keeps the code aligned with the rest of the BFS family and lets the implicit-graph step be a self-contained data-loading concern.

### Sub-section E: full execution trace — river-crossing, first few BFS steps

Start state: `{guards_left: 3, prisoners_left: 3, boat_side: "L"}`. The goal is `{0, 0, "R"}` — everyone across. Walk the first few steps of `create_prisoners_and_guards`:

The graph that emerges has 16 reachable states (the puzzle is small). After `create_prisoners_and_guards` returns, `solve_pg_bfs` runs the standard `breadth_first_search` from node 0 to get the parent array, then walks parent from node `visited["0,0,R"]` backwards to reconstruct the move sequence.

Final solution (one valid 11-move sequence):

```
step  state           who's on boat
────  ──────────────  ─────────────
 0    (3, 3, L)       —
 1    (3, 1, R)       2 prisoners cross
 2    (3, 2, L)       1 prisoner returns
 3    (3, 0, R)       2 prisoners cross
 4    (3, 1, L)       1 prisoner returns
 5    (1, 1, R)       2 guards cross

10    (0, 2, L)       1 prisoner returns

```

The state-space-BFS guarantees this is the *minimum* number of moves. Any shorter solution would imply BFS missed a shorter path, which would mean either the transition function is wrong or the visited-set hash is wrong.

### Move 2.5 — Brute force vs optimal (DSA addition)

The "brute force" approach is to try every move sequence up to some max depth and pick the shortest that ends at the goal — DFS with iterative deepening, in effect. The "optimal" approach for unweighted state spaces is BFS with state hashing.

**The data shape:**

```
PGState { guards_left: 0..3, prisoners_left: 0..3, boat_side: "L" | "R" }

Total possible states: 4 × 4 × 2 = 32
Reachable from (3,3,L) given the constraints: 16
```

**Brute force — DFS over move sequences with no memoization**

```
function solve_brute(state, depth, max_depth):
  if state.toString() == goal: return [state]
  if depth >= max_depth: return null
  for next in pg_neighbors(state):
    result = solve_brute(next, depth+1, max_depth)
    if result is not null:
      return [state, ...result]
  return null

// iterative deepening:
for d in 1..∞:
  result = solve_brute(initial, 0, d)
  if result: return result
```

Execution trace concept: at max_depth=11 (the right answer), the DFS explores millions of move sequences. Because there's no memoization, it revisits the same state via many different prefixes. For example, `(3,3,L) → (3,1,R) → (3,2,L)` and `(3,3,L) → (2,2,R) → (3,2,L)` both lead to `(3,2,L)` but DFS re-explores everything underneath it twice. The blowup is exponential in depth.

Complexity: O(b^d) time where b is branching factor (up to 5 here) and d is solution depth. For d=11, b=5: ~50 million calls. Space: O(d) for the recursion stack.

What goes wrong at scale: at the next-harder puzzle (4-guards, 4-prisoners, d≈15), brute force is ~30 billion calls. The 15-puzzle (d up to ~80, b up to 4) is ~10^48 calls — completely infeasible. Without state hashing, you re-solve subproblems forever.

**Optimal — BFS with state hashing**

The insight: every reachable state has *one* shortest distance from the start. BFS visits states in distance order, so the first time a state is enqueued, its distance is final. Storing the visited states by hash means each one gets processed exactly once. The total work is bounded by the *reachable* state-space size, not by `b^d`.

Trace was walked in Sub-section E. The whole BFS terminates after 16 dequeues — one per reachable state.

Complexity: O(S + S·b) time where S is the reachable-states count and b is branching factor. For the river puzzle, S=16, b≤5: ~80 calls total. Space: O(S) for visited + queue + materialized graph.

Why it's faster than brute force: hashing makes state-revisits free to detect, and BFS's distance-monotonic discovery means you never explore beyond the answer's depth. Brute force explored ~50 million paths to find an 11-step solution; BFS visited 16 states.

**Comparison**

```
┌─────────────────────┬─────────────────────┬─────────────────────┐
│                     │ Brute force (DFS    │ State-space BFS     │
│                     │ no memoization)     │                     │
├─────────────────────┼─────────────────────┼─────────────────────┤
│ Time                │ O(b^d)              │ O(S · b)            │
│ Space               │ O(d) stack          │ O(S) visited + queue│
│ River puzzle        │ ~50M calls          │ ~80 calls           │
│ 15-puzzle (10^13 S) │ ~10^48 — impossible │ ~10^14 — also bad   │
│ Shortest path?      │ requires deepening   │ guaranteed in 1 run │
│ Revisits states?    │ yes, infinitely     │ never (hash)        │
└─────────────────────┴─────────────────────┴─────────────────────┘
```

**When brute force is fine:** when the state space is so dense that hashing costs more than re-exploration (rare). Also when you can't define a stable hash key (graph isomorphism, where structurally-identical states have many representations). For the river-crossing puzzle, brute force is strictly worse.

### Move 3 — The principle

Many problems are graph-shaped without coming with a graph. The principle: if you can write a function `neighbors(state)` and a string `state.toString()` for hashing, you can run BFS on the resulting implicit graph. The whole search-algorithm family — BFS, DFS, Dijkstra, A* — generalises to any state-space where you can answer "what moves are legal from here?" The river-crossing puzzle is the small, tractable end of a spectrum that includes the 15-puzzle, Rubik's Cube, chess move-generation, scheduling problems, and theorem proving. Same shape, vastly different scale. The full picture is below.

## Elaborate

### Where this pattern comes from

State-space search predates computers — it's the formalization of how a logician explores "given these axioms and inference rules, can I derive that conclusion?" Allen Newell and Herbert Simon framed it computationally in the 1950s with the Logic Theorist and the General Problem Solver, which framed all problem-solving as walking a graph of states. The river-crossing puzzle is one of the canonical pedagogical examples — every AI textbook from Russell & Norvig down uses it because the state space is small (16 nodes) but the constraints are non-trivial. It generalises to scheduling, planning, and theorem proving via the same shape: state, transition, goal, search.

### The deeper principle

Implicit graphs. Every problem with discrete states, a transition rule, and a goal is graph-shaped — even if no one ever writes the edges down. The implicit-graph framing turns *most* combinatorial problems into search problems on a graph you generate as you go. Sudoku is implicit-graph search (state = grid, transitions = legal cell placements). Path-planning is implicit-graph search (state = position, transitions = legal moves). LLM tool use is implicit-graph search (state = current understanding, transitions = next tool call). The algorithm — BFS, DFS, A*, beam search — is the secondary choice; the *first* choice is recognising the problem as graph-shaped.

```
┌─ The implicit-graph generalization ────────────────────────────┐
│                                                                │
│  Problem            State                Transition            │
│  ──────────────     ──────────────────   ─────────────────     │
│  River crossing     PGState              pg_neighbors          │
│  Sudoku             grid w/ filled cells fill a cell legally   │
│  15-puzzle          tile positions       slide adjacent tile   │
│  Theorem proving    propositions known   inference rule        │
│  Tool-using agent   conversation+facts   next tool call        │
│  Form wizard        current step+answers valid next step       │
│                                                                │
│  All four pieces: state, transition, goal, search.             │
│  Pick search algorithm to match state-space size and weights.  │
└────────────────────────────────────────────────────────────────┘
```

### Where this breaks down

When the state space is too large to materialize even lazily. The river puzzle has 16 reachable states; the 15-puzzle has 10^13. Storing 10^13 entries in a `visited` dict is impossible in a browser tab. Two responses: (a) accept that you can't find the *globally* shortest path and use a heuristic-guided search (A*, IDA*, beam search) that prunes most of the state space; (b) accept that you can't store everything and use iterative-deepening DFS, which uses O(depth) memory and re-explores nodes — sometimes worth it. The line where this matters is roughly when `|S|` exceeds a few million.

Also breaks when state hashing isn't injective. If two distinct "logical" states produce the same `toString()`, BFS will conflate them and miss solutions. If equivalent states produce different strings (e.g., a Sudoku grid where row-permutations are isomorphic but you treat them as distinct), BFS revisits and bloats. Getting `toString()` right is the silent prerequisite that nobody warns you about.

### What we gave up

A second BFS pass. `create_prisoners_and_guards` runs one BFS-like walk to build the graph; `solve_pg_bfs` runs another (the standard `breadth_first_search`) to find the path. You could merge them — track parent during the discovery walk — but the split reuses the standard BFS implementation and keeps the two concerns (discover graph vs find path) separated. The cost is one extra O(V+E) pass through what's now a 16-node graph — invisible at this scale.

`Array.shift()` cost. The same O(n) per dequeue that BFS pays everywhere. For 16 nodes, irrelevant. For a 15-puzzle-scale problem, dominant — but at 15-puzzle scale, you'd switch to A* anyway, which uses a priority queue.

### What the alternative would have cost

If the river-crossing solver had pre-enumerated all 32 logically-possible `(guards_left, prisoners_left, boat_side)` configurations (4 × 4 × 2), constructed an edge list by checking every pair for validity, then run standard BFS:

```
// pre-enumeration approach
for g in 0..3:
  for p in 0..3:
    for side in ["L", "R"]:
      state = PGState(g, p, side)
      if is_valid(state):
        nodes.push(state)
        // then O(S²) double-loop checking every pair for an edge
```

The total enumeration is 32 states (small), but the edge-construction loop is 32² = 1024 candidate edges to validate. For this puzzle that's negligible — but the structural cost is worse: changing the puzzle's rules (boat capacity = 3, two boats, an extra constraint) means rewriting both the validity check *and* the edge generation. State-space BFS pushes all the puzzle-specific logic into one function (`pg_neighbors`) which is easier to evolve.

And the pre-enumeration would have wasted work on states unreachable from the initial configuration. The implicit form visits only reachable states; the enumeration form has to either enumerate everything or pre-prune.

### The breakpoint

Fine until the reachable state space exceeds a few million entries — at that point the `visited` dict is a memory hot spot. Fine until moves have varying cost — at that point you need Dijkstra (priority queue) over the implicit graph. Fine until BFS without guidance is exploring far too much of the state space before finding the goal — at that point you need A* with a heuristic. For the river-crossing puzzle (16 states, 11-move solution), none of these breakpoints are remotely near.

### What wasn't actually a tradeoff

Materializing the entire `Graph2` once and reusing it across solver calls. `solve_pg_bfs` builds the graph every time it's called — and the UI calls it on every boat-click. The total work is ~80 operations × N clicks. Caching the graph between calls would be a real perf win (avoid 80 ops per click) but the move-validation flow already runs in well under a millisecond, so it's not a meaningful concern. Caching would add complexity without observable benefit.

## Tech reference (industry pairing)

### `Graph2` grown via `insertNode`

- **Codebase uses:** `g.insertNode(state)` in `PG.ts` L97, L121. The `Graph2.insertNode` method (`Graph2.ts` L136–L142) pushes a new `Node2` onto the array and increments `numNodes`.
- **Why it's here:** the implicit graph needs a place to live as it's discovered; `Graph2`'s push-and-grow model fits the discovery pattern perfectly.
- **Leading today:** mutable graph structures for state-space search — adoption-leading, 2026.
- **Why it leads:** matches the discovery pattern of every search algorithm; no upfront allocation; debuggable via plain JS.
- **Runner-up:** persistent/immutable graph structures (e.g., `Map`-of-`Map`s with structural sharing) — innovation-leading in functional-language ecosystems (Clojure, ReScript), not common in JS.

### Plain JS object as visited-set

- **Codebase uses:** `const visited = {} as any;` in `PG.ts` L92, keyed by `state.toString()`.
- **Why it's here:** O(1) check whether a state has been seen, with a string key derived from the state's fields.
- **Leading today:** plain JS objects for small dictionaries — adoption-leading; `Map` for larger ones — innovation-leading.
- **Why it leads:** zero dependency, ergonomic syntax, JIT-friendly for string keys.
- **Runner-up:** `Map<string, number>` — proper `.size`, ordered iteration, no prototype-pollution risk. For 16 states the difference doesn't matter; at scale, `Map` is the right choice.

### `state.toString()` as hash key

- **Codebase uses:** `${this.guards_left},${this.prisoners_left},${this.boat_side}` in `PG.ts` L15.
- **Why it's here:** state identity is field-equality, not reference-equality. Two `PGState` objects with the same field values must hash to the same key. Template literals concatenate cheaply and produce a stable string.
- **Leading today:** structural string keys for state-space hashing — adoption-leading.
- **Why it leads:** simplest reliable encoding; trivially debuggable; no risk of object-identity false negatives.
- **Runner-up:** bit-packed integer encoding (e.g., `(guards * 8) + (prisoners * 2) + boat_side_bit`) — innovation-leading when state space is huge and string allocation costs matter. For 16 states, overkill.

## Summary

State-space BFS is BFS over a graph generated on the fly by a transition function. In `PG.ts`, `pg_neighbors` produces the next valid states from any current `PGState`; `create_prisoners_and_guards` walks every reachable state once and materializes them as a `Graph2`; `solve_pg_bfs` then runs the standard `breadth_first_search` to find the shortest move sequence from the start to a goal state. The constraint that made the implicit form the right call is that the puzzle's rules — not just its states — define the graph; rewriting the rules (capacity, constraint count, multiple boats) means changing one transition function instead of regenerating an edge list. The cost is two passes (discover + path-find) and the standard `Array.shift()` O(n) per dequeue, both negligible at 16 states.

- State = `PGState` object; transition = `pg_neighbors`; the graph is generated, not stored.
- `state.toString()` is the hash key; it must be injective for BFS to be correct.
- BFS is run twice: once to discover the state space (lazy graph build), once for path-finding via standard `breadth_first_search`.
- The reachable state space (16 states for the river puzzle) is all that gets materialized — unreachable states never allocate.
- Pattern generalises: sudoku, 15-puzzle, theorem proving, scheduling, LLM tool use — all state-space search with different state shapes and scales.

## Interview defense

### What an interviewer is really asking

When the interviewer hands you a puzzle ("river-crossing," "Tower of Hanoi," "missionaries and cannibals") and asks "find the shortest solution," they're checking whether you immediately recognise it as graph search. The follow-up — "but there's no graph here, just a set of rules" — is the test for whether you can see implicit graphs. Half of senior algorithms questions are problems disguised as something else; the question behind the question is "can you abstract this into BFS over (state, transition)?"

### Likely questions

[mid] Q: How would you find the shortest solution to a sliding-tile puzzle?

A: I'd treat it as BFS over an implicit graph. State = the current tile arrangement (e.g., a string `"123456780"` where 0 is the blank). Transition = the legal slides from the current state — up to four, depending on where the blank is. Visited set keyed by the state string. Standard BFS-with-parent: enqueue the start, pop, generate neighbors via the transition function, push unvisited, record parent on each push. When you dequeue the goal state, walk parent backwards to reconstruct the move sequence. The whole thing is BFS — just with `neighbors()` computed instead of looked up.

Diagram:

```
state-space BFS shape

  initial state ──► visited[state.toString()] = true
       │            queue = [initial]
       ▼
  while queue.length:
       u = queue.shift()
       for state in neighbors(u):      ← transition function
         key = state.toString()
         if key not in visited:
           visited[key] = true
           parent[state] = u
           queue.push(state)
       if u == goal: break
```

[senior] Q: The river-crossing puzzle has 16 states. What changes in your approach if it has 10^13 states (the 15-puzzle)?

A: Three layers. The `visited` dict won't fit — you can't store 10^13 keys in any browser tab. The `Graph2` materialization is impossible for the same reason. And uninformed BFS would explore most of the state space before reaching the goal. The fix is A* with a heuristic — for the 15-puzzle, the standard heuristic is sum-of-Manhattan-distances of each tile from its goal position. A* prioritises states with low `(cost_so_far + heuristic)` and prunes the explored set by 99%+. You also drop the `visited` dict in favour of a "closed list" plus a transposition table with a bounded size — accepting that some re-exploration is the cost of fitting in memory.

```
│                          in any RAM             │
└─────────────────────────────────────────────────┘
┌─ Materialized graph ────────────────────────────┐
│  10^13 Node2 objs   ◀── BREAKS: same problem    │
└─────────────────────────────────────────────────┘
┌─ Search strategy ───────────────────────────────┐
│  uninformed BFS     ◀── BREAKS: explores ~99%   │
```

[arch] Q: The UI calls `solve_pg_bfs` on every boat-click. What's the architectural concern there, and how would you redesign?

A: Two concerns. Performance: the graph gets rebuilt from scratch on every click — ~80 operations, milliseconds, but redundant. Coupling: the UI's logic ("is this move valid?") delegates to a search algorithm ("does a solution exist from this state?"), which conflates *legal move* with *winnable position*. Both are useful, but the UI mostly wants the former. I'd refactor in two steps. First, cache the materialized `Graph2` at module load — `create_prisoners_and_guards` runs once, results stored. Second, expose two predicates: `is_move_valid(state, move)` (constant-time) and `is_winnable_from(state)` (graph lookup against the cached graph). The UI calls the first to reject impossible moves and the second to detect dead-ends.

Diagram:

```
Current architecture vs refactored

  Now:                            Better:
  click → solve_pg_bfs(newState)   click → is_move_valid?
           │                                │
           ▼                                ▼  (yes)
       rebuild graph                  is_winnable_from?
       run full BFS                        │
       check result                        ▼ (no)
                                       reject move
  ─────────────────────────────────  ──────────────────────
  ~80 ops per click                  ~5 ops per click + 1
                                     graph lookup
```

### The question candidates always dodge

Q: Why build the whole `Graph2` if you're just going to run BFS over it anyway? Why not merge the two passes and track parents during the discovery walk?

A: Because the two passes have different jobs. `create_prisoners_and_guards` discovers the state space — it doesn't know what the eventual goal is, so it can't usefully track parents. (Parents only make sense relative to a specific BFS run; the discovery walk could be parented to *anything*.) Then `solve_pg_bfs` runs the standard `breadth_first_search` from whatever start state it wants, against the now-materialized graph, with parent-tracking specific to that BFS run. The cost is one extra O(V+E) pass — at 16 nodes, invisible. The benefit is reuse of the standard `breadth_first_search`: any improvement to that function (deque optimisation, animation hook, A* variant) automatically lifts this caller. Merging them would couple the discovery walk to the path-find concern and lose that reuse. The "two passes is wasteful" argument is correct at scale (where you'd switch to A* anyway) and wrong here.

Diagram:

```
│                  │ and_guards            │ tracking            │

│ Extensibility    │ swap path-finder for  │ rewrite whole loop  │
│                  │ Dijkstra/A* freely    │                     │

The 80-op saving isn't worth the lost reuse and clearer separation.
```
